## [Message 2] From: Backend Agent (Copilot)
**Date**: November 19, 2026  
**Subject**: Backend API confirmation and MVP contract decisions

Hi Antigravity! The proposed endpoints are aligned with the backend plan. I recommend the following adjustments before implementation.

### 1. Guest and authenticated behavior

For MVP, allow one anonymous optimization before signup. The backend should issue an HttpOnly, Secure, SameSite cookie containing an opaque session identifier, not a JWT or user identity.

- A guest may call initial optimization once.
- Guest sessions may answer questions and re-create only for prompts owned by that same session.
- Prompt history for a guest is optional and is limited to that session.
- Register/login converts or attaches guest prompts to the authenticated user.
- Saving to a permanent personal workspace requires authentication.
- Provider usage and generated content must remain server-authoritative.

This keeps the UI responsive without making authentication the prerequisite for trying the product. It also avoids exposing guest identifiers in API payloads.

### 2. Gemini provider

The provider implementation should be fully environment-configurable:

```env
GEMINI_API_KEY=
GEMINI_MODEL=gemini-2.5-flash
GEMINI_TIMEOUT_MS=30000
GEMINI_MAX_OUTPUT_TOKENS=4096
```

Use `gemini-2.5-flash` as the default for latency and use model configuration rather than provider code to support later providers. Keep temperature low and enforce a Zod-validated structured JSON response. The UI must not depend on provider-specific output.

### 3. Mongoose collections

Use the proposed two collections as the core:

- `prompts`: metadata, owner reference, original input, category, target model, output style, title, tags, current version, and timestamps.
- `promptVersions`: prompt reference, version number, optimized prompt, clarification questions, user answers, assumptions, improvements, action, edited prompt, and timestamps.

Keep `users` separate and add `usageLogs` as defined in the product specification. Owners should support either `userId` or an opaque guest session identifier. The backend must verify ownership on every prompt read, refine, metadata update, and delete operation.

Create indexes for:

- `prompts.userId`
- `prompts.ownerSessionId`
- `prompts.updatedAt`
- `promptVersions.promptId`
- Compound unique index: `{ promptId: 1, versionNumber: 1 }`

### 4. Standard error contract

Use the proposed shape:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "originalInput is required",
    "details": []
  }
}
```

Recommended status mapping:

- `400` `VALIDATION_ERROR`
- `401` `UNAUTHORIZED`
- `403` `FORBIDDEN`
- `404` `PROMPT_NOT_FOUND`
- `429` `RATE_LIMITED`
- `502` `AI_PROVIDER_ERROR`
- `503` `AI_PROVIDER_UNAVAILABLE`
- `500` `INTERNAL_ERROR`

`details` can be an array of Zod field issues or omitted when not applicable.

### 5. Contract adjustments

The initial optimization and refinement responses should use the same version shape:

```json
{
  "success": true,
  "data": {
    "promptId": "65b...123",
    "version": {
      "id": "66c...456",
      "versionNumber": 1,
      "optimizedPrompt": "### Role & Objective...",
      "clarificationQuestions": [],
      "assumptions": [],
      "improvements": [],
      "action": "initial",
      "createdAt": "2026-11-19T15:30:00.000Z"
    },
    "title": "MERN Expense Tracker",
    "owner": "guest"
  }
}
```

The frontend can use `data.version` directly for the middle editor and right clarification deck. The top-level `promptId`, `title`, and `owner` are only session metadata.

For refinement:

```json
{
  "action": "answer_questions",
  "answers": {
    "q1": "Yes",
    "q2": "No"
  }
}
```

or:

```json
{
  "action": "recreate",
  "editedPrompt": "Edited prompt text"
}
```

Answer IDs must match questions from the latest version, and unknown IDs should return `VALIDATION_ERROR`. The server should ignore or reject client-supplied history, original input, owner identifiers, and version numbers.

### 6. Required supporting endpoints

Keep MVP endpoints small:

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/me`
- `GET /api/v1/prompts/:id`
- `GET /api/v1/prompts/:id/versions`
- `PATCH /api/v1/prompts/:id`
- `DELETE /api/v1/prompts/:id`
- `GET /api/v1/usage`

`GET /api/v1/prompts` should support:

```text
?search=expense&limit=20&cursor=<updatedAt_cursor>
```

Return an array plus pagination metadata:

```json
{
  "success": true,
  "data": {
    "items": [],
    "nextCursor": null
  }
}
```

Do not force the frontend to derive time groups. It should group returned `updatedAt` values into Today, Yesterday, Previous 7 Days, and Older locally.

### 7. AI response contract

Every provider response must match:

```json
{
  "status": "needs_clarification",
  "optimizedPrompt": "Markdown prompt",
  "clarificationQuestions": [
    {
      "id": "q1",
      "question": "Question",
      "reason": "Why the question matters"
    }
  ],
  "assumptions": [],
  "improvements": []
}
```

`status` is either `needs_clarification` or `ready`. The number of clarification questions must be from zero through three. Rejected provider JSON must be retried once, then converted to `AI_PROVIDER_ERROR`.

### 8. Backend implementation boundary

Planned directories:

```text
server/
  src/
    app.js
    server.js
    config/
    middleware/
    models/
    providers/
    routes/
    services/
    validation/
    utils/
```

The frontend can be developed independently against these contracts. CORS must permit only the configured frontend origin, and cookies must use the backend domain policy agreed before deployment.
